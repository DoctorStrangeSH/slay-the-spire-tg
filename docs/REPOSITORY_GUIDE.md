# Руководство по репозиторию

Краткая карта проекта для разработчиков и участников приёмки. Продуктовые требования определяет [PROJECT_SPEC.md](PROJECT_SPEC.md), очередность работ — [ROADMAP.md](ROADMAP.md).

## 1. Технологическая схема

Проект — статическое клиентское веб-приложение:

- HTML — каркас экранов и последовательность загрузки.
- CSS — адаптивный интерфейс и визуальная система «Тёмный собор».
- JavaScript без сборщика и без npm-зависимостей — игровые данные, логика и UI.
- Node.js 22 — синтаксическая проверка и встроенный Test Runner.
- GitHub Pages — браузерная публикация.
- Telegram WebApp SDK — интеграция при открытии Mini App.

Точка входа — `index.html`. Скрипты подключаются обычными тегами в заданном порядке. Порядок не произвольный: конфигурация и данные должны быть доступны игровым системам, системы — интерфейсу, а `js/main.js` загружается последним.

## 2. Где искать изменения

| Путь | Ответственность |
|---|---|
| `index.html` | Каркас экранов, версия сборки, порядок подключения ресурсов |
| `css/style.css` | Базовые стили |
| `css/cathedral.css` | Тема «Тёмный собор», игровые экраны и адаптивная компоновка |
| `js/config/constants.js` | Общие константы, типы карт и комнат |
| `js/data/heroes.js` | Реестр героев и стартовые параметры |
| `js/data/cards/` | Карты классов и общий пул |
| `js/data/enemies.js` | Противники и боссы |
| `js/data/relics.js` | Реестр реликвий |
| `js/systems/Game.js` | Координация забега, событий, комнат и переходов |
| `js/systems/MapGenerator.js` | Генерация карты и маршрутов |
| `js/systems/RunSave.js` | Локальные checkpoint и восстановление забега |
| `js/systems/RunHistory.js` | История завершённых забегов |
| `js/systems/battle/` | Разделённые части боевого ядра |
| `js/systems/BattleSystem.js` | Связующий слой боевой системы |
| `js/ui/` | Экранные компоненты и визуальное представление |
| `tests/` | Регрессионные и сценарные проверки |
| `docs/` | ТЗ, аудит, дорожная карта и инструкции |

### Границы ответственности

- Игровые значения хранятся в реестрах данных и игровых системах, а не дублируются в UI.
- UI показывает состояние игры и передаёт намерения игрока игровым системам; он не должен самостоятельно пересчитывать исход боя.
- Прогноз боя должен использовать те же правила и модификаторы, что и фактическое разрешение действия.
- Сохранение должно восстанавливать проверяемое состояние забега и отклонять повреждённые данные без частичного применения.
- Изменение одного игрового правила требует регрессионного теста на само правило и, если применимо, на прогноз/отображение этого правила.

## 3. Проверки перед изменением

Нужен Node.js 22 или новее.

```bash
# Синтаксис всех исходных и тестовых JS-файлов
find js tests -type f \( -name '*.js' -o -name '*.cjs' \) -print0 | xargs -0 -n1 node --check

# Полный набор регрессионных тестов
node --test tests/*.test.cjs
```

GitHub Actions запускает обе проверки на push в `main` и для pull request. Изменение нельзя считать проверенным, пока CI не завершился успешно.

Для узкой отладки можно запускать один файл:

```bash
node --test tests/run-save.test.cjs
```

## 4. Правила внесения изменений

1. Сначала сверяйтесь с [PROJECT_SPEC.md](PROJECT_SPEC.md) и [ROADMAP.md](ROADMAP.md).
2. Не расширяйте замороженный объём 1.0. Новая система, класс, акт или крупная механика требуют отдельного решения после релиза.
3. Исправляйте первопричину, не маскируйте дефект ослаблением теста. Если тест содержит неверное предположение, подтвердите это фактическим контрактом и замените проверку на точную.
4. Добавляйте тест, который падает до исправления и проходит после него.
5. Не меняйте баланс и контент в рамках технической уборки.
6. Не проводите массовое форматирование или механическое переименование больших файлов без отдельной необходимости: это затрудняет ревью и может скрыть игровые изменения.
7. Не удаляйте документацию и историю аудита только из-за размера. Сначала убедитесь, что информация перенесена и больше не нужна.
8. Не коммитьте токены, секреты, локальные сохранения, логи, кэши, зависимости и результаты сборки.

## 5. Комментарии в коде

Комментарии должны помогать сопровождать код, а не пересказывать следующую строку.

- Оставляйте пояснения для игровых инвариантов, неочевидного порядка эффектов, совместимости сохранений и особенностей Telegram WebView.
- Удаляйте комментарии, которые описывают уже удалённый код, повторяют очевидную операцию или ссылаются на временную отладку.
- Не удаляйте лицензионные уведомления, авторские атрибуции и обязательные notices.
- Не оставляйте в исходниках персональные заметки об использованной модели или помощнике. История авторства и лицензирования должна оставаться корректной.

## 6. Версия и публикация

При каждом изменении JavaScript или CSS, предназначенном для пользователей, обновите метку версии в `index.html` и все соответствующие query-параметры ресурсов. Они должны совпадать.

Порядок публикации и ограничения Telegram WebView описаны в [DEPLOYMENT.md](DEPLOYMENT.md). Не публикуйте токен Telegram-бота в клиентском коде.
